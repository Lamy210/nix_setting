# Design: GUI self-update Step 2

## D1. Staged activation

Implementation readiness and shipping activation are separate states.

Phase A (this change may merge):
- manifest generator + tests
- updater backend integration
- frontend UX / fallback
- release workflow contract
- updater disabled unless a valid production public key/endpoints are compiled in

Phase B (shipping activation):
- macOS Final Acceptance PASS
- production Tauri updater key pair generated by the user
- private key + password stored in GitHub Actions secret and offline backup
- public key reviewed and committed/configured
- tag release produces signed updater artifact + latest.json
- real macOS N -> N+1 update E2E passes

No placeholder or test key may be shipped as production trust root.

## D2. Rust backend owns updater API

The frontend remains the existing static Vanilla JS bundle.
Use Rust-side `tauri-plugin-updater` APIs and expose:
- `fetch_app_update` -> optional serializable metadata
- `install_app_update` -> downloads/installs the previously checked update
- progress -> `app-update-progress` event
- explicit restart command/path after successful install

Pending update is stored in Tauri managed state using `Mutex<Option<Update>>`,
matching the official Tauri 2 command pattern.

Reasons:
- no npm/package.json layer is required
- security-sensitive updater configuration remains Rust/config-side
- frontend/backend command-name regression testing already exists

## D3. Platform behavior

macOS aarch64:
- updater may be enabled after activation gate
- automatic check/install available

Linux:
- updater remains disabled
- Dashboard retains GitHub Releases/update guidance

Windows:
- desktop distribution is not provided; updater disabled

The Releases link remains visible as fallback even on macOS.

## D4. Static latest.json

Use Tauri static JSON format:

```json
{
  "version": "0.3.0",
  "notes": "...",
  "pub_date": "2026-XX-XXT00:00:00Z",
  "platforms": {
    "darwin-aarch64": {
      "url": "https://github.com/Lamy210/nix_setting/releases/download/v0.3.0/<updater-artifact>",
      "signature": "<contents of .sig>"
    }
  }
}
```

Generator inputs:
- tag/version
- updater artifact filename/URL
- signature file
- optional notes/pub_date

Generator validation:
- SemVer-compatible version
- non-empty HTTPS URL
- non-empty signature
- only `darwin-aarch64` in this phase
- deterministic JSON output

## D5. Release signing boundary

Tauri updater signatures are mandatory.

Tag release activation requires:
- `TAURI_SIGNING_PRIVATE_KEY`
- corresponding password secret when the key is encrypted
- configured public key in the shipped app

PR CI must not require production private key.
Updater artifact creation is therefore enabled only in the tag release path, not ordinary PR DMG build.

The existing DMG remains a manual-install fallback and continues to pass portability gates.

## D6. Fail-closed UX

- check failure: show non-destructive error + Releases link
- signature mismatch / install failure: existing app remains unchanged
- no pending update: install command returns explicit error
- updater disabled build: frontend does not show auto-update action
- no downgrade support in this phase

## D7. Verification

PR CI:
- OpenSpec strict
- updater manifest generator fixture tests
- static config/release workflow contract
- desktop cargo test / fmt / clippy / build smoke
- frontend/backend command mapping

Activation E2E after key provision:
1. install version N DMG
2. publish signed N+1 updater artifact + latest.json
3. check from N
4. download/install N+1
5. restart app
6. verify N+1 version
7. tampered updater artifact must fail signature verification without replacement
